# stock-wiki 사이트 구축 설계 문서

- 작성일: 2026-07-30
- 상태: 사용자 승인 완료 (사이트 틀·구조 확정)
- 선행 문서: [2026-07-27-stock-wiki-design.md](2026-07-27-stock-wiki-design.md) (콘텐츠 설계, 8장에 사이트 요구사항)
- 인계 문서: [../../handoffs.md](../../handoffs.md) (8장이 이 프로젝트로 넘긴 사항)

## 1. 개요

39개 챕터로 계획된 마크다운 콘텐츠(현재 13개 완성 — 파트 1의 6개, 파트 2의 7개)를 게시할 정적 사이트를 구축한다. 목적은 검색 유입 기반의 애드센스 수익화이며, 콘텐츠 집필은 이 프로젝트와 병행해서 계속 진행된다.

**이 프로젝트의 제1 제약**: 기존 마크다운 파일을 수정하지 않는다. 파트 3 집필이 별도 세션에서 병행되므로, 사이트 구축이 콘텐츠 파일을 건드리면 충돌한다.

## 2. 사이트 틀 결정 — VitePress

선택을 가르는 기준을 4개로 압축했다. 39개 챕터 규모에서는 빌드 속도·생태계 크기가 결정에 영향을 주지 않으므로 제외했다.

1. **기존 상대링크 `.md` 보존** — 본문에 `](2-4-ipo-subscription.md)`, `](../part1-basics/1-3-how-to-buy-stocks.md)` 형태의 링크가 100곳 이상 있다. 일괄 치환이 필요한 도구는 제1 제약을 위반한다.
2. **한국어 토크나이저 제어권** — 조사·어미가 붙은 본문을 잡으려면 검색 인덱스의 토큰화 함수를 교체할 수 있어야 한다.
3. **광고 슬롯 삽입 경로** — 본문 상단·중간·하단에 컴포넌트를 끼워 넣을 공식 확장점이 있는지.
4. **챕터 추가 시 손댈 곳** — `.md` 하나를 커밋하면 목차·검색·사이트맵이 자동 갱신되어야 한다.

| 기준 | VitePress (채택) | Astro + Starlight | Hugo + Hextra |
|---|---|---|---|
| 상대링크 `.md` | 네이티브 해석 → 클린 URL 자동 변환 | 콘텐츠 컬렉션 외부 파일 loader 설정 + rehype 플러그인 필요 | 별도 처리 필요 |
| 한국어 검색 | MiniSearch 기반, `tokenize` 교체 가능 | Pagefind 내장, 토크나이저 교체 불가 | FlexSearch, Go 템플릿 경유로 불투명 |
| 광고 슬롯 | 기본 테마 슬롯(`doc-before`/`doc-after`) 제공 | 컴포넌트 오버라이드 | partial 오버라이드 (쉬움) |
| 3단 레이아웃 | 기본값 | 기본값 | 테마 제공 |
| SEO 기본 제공 | 수동 설정 | 가장 강함 | 중간 |

**채택 이유**: 이 저장소는 이미 "폴더에 마크다운이 쌓여 있고 서로 상대경로로 링크된" 구조이고, VitePress가 정확히 그 구조를 사이트로 바꾸는 도구다. 나머지 두 안은 콘텐츠를 도구 구조에 맞춰 옮기거나 링크를 바꿔야 하므로 제1 제약과 충돌한다.

**기각 근거 보강**:
- Astro + Starlight은 종합 완성도(특히 SEO 기본 제공)가 가장 높으나 기준 1·2에서 모두 밀린다. Pagefind는 질의의 마지막 단어에만 접두어 매칭을 걸기 때문에 「공매도」 단독 검색은 잡히지만 「공매도 재개」처럼 두 단어 이상이면 앞 단어가 정확 일치로 처리되어 구멍이 남는다.
- Hugo는 Node 없이 빌드되는 것이 최대 이점이나, handoffs 8장이 mermaid 4건의 실제 렌더 검증을 이 프로젝트 숙제로 넘겼으므로 Node는 어차피 도입된다. 이점이 상쇄된다.

## 3. 저장소 구조

사이트 코드를 `stock-wiki` 저장소 안에 둔다. 콘텐츠와 사이트가 한 저장소에 있으면 챕터 커밋이 곧 재배포이며 동기화 장치가 필요 없다.

```
stock-wiki/
├── .vitepress/
│   ├── config.mts              사이트 설정 · 검색 · 사이트맵 · SEO 헤드
│   ├── sidebar.ts              part*/ frontmatter 스캔 → 목차 트리 생성
│   ├── korean-search.ts        한국어 토크나이저 (색인용 · 질의용)
│   ├── planned-links.ts        미집필 챕터 링크 처리 markdown-it 플러그인
│   ├── mid-content-ad.ts       본문 중간 광고 삽입 markdown-it 플러그인
│   └── theme/
│       ├── index.ts            기본 테마 확장 · 슬롯 주입
│       ├── AdSlot.vue          광고 자리 (발행자 ID 없으면 렌더 안 함)
│       └── style.css           「집필 예정」 표시 등 커스텀 스타일
├── index.md                    랜딩 페이지 (신규)
├── about/
│   ├── privacy.md              개인정보처리방침 (신규)
│   ├── disclaimer.md           면책조항 (신규)
│   └── contact.md              문의 (신규)
├── public/
│   ├── robots.txt
│   └── ads.txt                 발행자 ID 확정 후 채움
├── part1-basics/ … part7-trends/   기존 그대로 — 수정하지 않음
├── .nvmrc                      Node 22 고정
├── .gitignore                  node_modules · dist · cache
├── package.json
├── README.md                   깃허브용으로만 유지 (사이트 제외)
└── docs/, .superpowers/        사이트 제외
```

### 3.1 사이트 제외 대상 (`srcExclude`)

`srcDir`이 저장소 루트이므로 명시적으로 제외하지 않으면 내부 작업 문서가 웹에 공개된다.

- `README.md` — 깃허브 진입점으로 유지. 사이트 목차는 사이드바가 담당하므로 중복 불필요
- `docs/**` — `handoffs.md`, `chapter-template.md`, 설계 문서, 계획서
- `.superpowers/**` — sdd 작업 로그, 리뷰 diff
- `node_modules/**`

**빌드 산출물에 `handoffs.md`가 포함되지 않는지를 완료 판정 기준에 넣는다.** 이 문서에는 미검증 수치, 출처 추적 메모, 집필 판단 근거가 들어 있어 독자용 콘텐츠가 아니다.

## 4. URL 설계

```
part2-korea-market/2-7-short-selling.md
  → https://stock-wiki.digestive-coffee.blog/part2-korea-market/2-7-short-selling
```

`cleanUrls: true`로 `.html` 확장자를 없앤다.

**VitePress `rewrites`를 쓰지 않는다.** rewrites로 번호·폴더를 제거해 `/short-selling` 같은 짧은 주소를 만들 수 있으나, rewrites를 켜면 상대링크가 재작성된 경로 기준으로 해석되어 본문의 상대링크 100여 곳을 전부 수정해야 한다. 제1 제약과 충돌한다.

SEO 손실은 사실상 없다. 슬러그가 영문이므로 한국어 검색 질의에 기여하는 분량이 어느 쪽이든 거의 없다.

## 5. 목차 트리 자동 생성

`part1-basics` ~ `part7-trends` 폴더의 `.md` 파일 frontmatter를 스캔해 사이드바를 생성한다.

- 정렬: `part` → `order` 오름차순
- 그룹 제목: 파트명 (선행 설계 문서 5장의 확정 목차 기준)
- **39개 전체를 표시하되 미집필 26개는 비활성 상태**로 둔다. 위키독스식 책의 전체 그림을 보여주고, 계속 채워지는 책이라는 신호를 준다. `.md` 파일이 생기면 자동 활성화된다.
- 파트 7은 목차가 고정되지 않은 수시 추가 파트다. 하드코딩된 챕터 목록 없이 폴더의 실제 파일만 나열한다.

미집필 챕터의 제목은 파일이 없으므로 frontmatter에서 읽을 수 없다. 선행 설계 문서 5장의 확정 목차를 `.vitepress/` 안의 데이터로 두고, 파일이 있으면 frontmatter를, 없으면 이 목차를 쓴다.

**이로써 목차가 세 곳에 존재하게 된다** — 선행 설계 문서 5장(확정 근거), `README.md`(깃허브 진입점), `.vitepress/` 데이터(사이드바용). 챕터 제목이 바뀌면 세 곳이 어긋날 수 있다. 다만 이 중복은 시한부다. 39개가 모두 집필되면 `.vitepress/` 데이터는 필요 없어지고 frontmatter만 남는다. 그때까지는 사이드바 데이터가 유일한 자동 검증 지점이므로, 파일이 있는데 목차 데이터에 없는 챕터(또는 반대)가 나오면 빌드 시 경고를 띄운다.

## 6. 미집필 챕터 링크 처리

현재 본문에 아직 존재하지 않는 챕터를 가리키는 링크가 **14곳, 7개 챕터**(3-2, 3-3, 3-5, 3-6, 4-4, 4-5, 5-2)에 있다. VitePress는 기본적으로 깨진 링크가 있으면 빌드를 실패시킨다.

**채택**: 빌드 시 링크 대상 파일의 존재를 확인해, 없으면 링크를 제거하고 「집필 예정」 표시가 붙은 텍스트로 렌더하는 markdown-it 플러그인을 만든다. 마크다운 원본은 수정하지 않는다. 파트 3을 집필하면 해당 링크가 자동으로 살아난다.

**기각한 대안**:
- 스텁 페이지 생성 — 내용 없는 페이지가 색인되면 애드센스 심사와 SEO에 불리하다.
- `ignoreDeadLinks: true` — 링크가 404로 남는다. 진짜 오타 링크도 검출되지 않는다.

`ignoreDeadLinks`는 끈 채로 유지해, 계획된 챕터가 아닌 오타 링크는 빌드를 실패시킨다.

## 7. 한국어 검색

VitePress 로컬 검색(MiniSearch 기반)을 쓰고, 색인용과 질의용에 서로 다른 토크나이저를 설정한다.

| | 규칙 | 예: 본문 「공매도는 논란이 많아요」 |
|---|---|---|
| **색인 시** | 한글 덩어리를 길이 2 이상 모든 접두어로 분해 | `공매` `공매도` `공매도는` `논란` `논란이` `많아` `많아요` |
| **질의 시** | 분해 없이 덩어리 그대로 | 질의 「공매도」 → `공매도` |

질의어 `공매도`가 색인의 `공매도` 토큰과 일치한다. 「공매도를」 「공매도가」 「공매도에」도 같은 접두어를 낳으므로 함께 잡힌다.

- **가능한 모든 부분문자열을 넣는 n-gram 방식은 기각.** 인덱스가 5~10배로 커지고 오탐이 늘어나는데, 한국어에서 실제 문제는 뒤에 붙는 조사·어미이므로 접두어 분해로 정확히 해결된다. 색인 증가는 2배 수준이다.
- 영문·숫자는 소문자화만 하고 분해하지 않는다 (ETF, PER, S&P500).
- **알려진 한계**: 「공매도」로 붙여쓴 합성어 「무차입공매도」는 잡지 못한다. 본문은 「무차입 공매도」처럼 띄어 쓰고 있어 실제 영향은 작다고 판단했다.

### 7.1 검색 UI — 모달

선행 설계 문서 8장은 "검색 결과 페이지가 나오고 클릭하면 챕터로 이동"으로 적었으나, **모달 오버레이로 변경한다.** 결과 목록·본문 발췌·클릭 이동이라는 동작은 동일하고 `/search?q=` 형태의 고유 주소만 없다.

**변경 근거**: 구글은 사이트 내부 검색 결과 페이지의 색인을 저품질 신호로 취급한다. 별도 페이지를 만들면 `noindex` 처리를 따로 해야 하고 얻는 것은 검색 결과 URL 공유 기능 하나뿐이다. 애드센스 승인이 이 프로젝트의 목적이므로 모달을 택한다.

### 7.2 검색 검증

토크나이저가 의도대로 동작하는지 추측으로 끝내지 않는다. 실제 색인을 만들어 조사가 붙은 본문을 잡는지 확인하는 테스트를 붙인다. 최소 케이스: `공매도`, `배당락`, `서킷브레이커`, `액면분할`.

## 8. mermaid

`vitepress-plugin-mermaid`를 도입한다. 라이트/다크 모드에 따라 다이어그램 테마도 전환되게 맞춘다.

**이것으로 handoffs 8장의 숙제가 해결된다** — 1-1, 1-2, 2-4, 2-7의 mermaid 다이어그램 4건은 지금까지 정적 문법 검사만 거쳤고 실제 렌더를 확인한 사람이 없다. 이 단계에서 렌더가 깨지면 다이어그램 문법 수정이 필요하며, 이는 제1 제약(마크다운 수정 금지)의 유일한 예외로 허용한다.

## 9. 광고 (애드센스)

애드센스는 아직 미신청 상태다. 발행자 ID가 설정되지 않으면 `AdSlot.vue`가 아무것도 렌더하지 않게 만들고, 승인 후 ID만 넣으면 전 페이지에 한꺼번에 켜지게 한다.

**배치** — 챕터 본문이 70~130줄로 짧아 광고 3개는 본문 대비 과하다. 다음과 같이 조절한다.

| 위치 | 적용 범위 | 구현 |
|---|---|---|
| 본문 상단 (제목 아래) | 전 챕터 | 테마 `doc-before` 슬롯 |
| 본문 하단 (이전/다음 링크 위) | 전 챕터 | 테마 `doc-after` 슬롯 |
| 본문 중간 (3번째 `##` 앞) | `##` 섹션 4개 이상인 챕터만 | markdown-it 플러그인 |

`public/ads.txt`도 발행자 ID가 필요하므로 승인 후 채운다. 지금은 파일 자리만 만든다.

## 10. 정책 페이지

애드센스 심사 통과에 사실상 필수인 3개 페이지를 만들고 푸터에서 전 페이지에 링크한다.

- **`about/privacy.md`** — 개인정보처리방침. 이 사이트가 직접 수집하는 정보가 없다는 점, 구글 및 제3자 공급업체가 광고 쿠키를 사용한다는 점, 사용자가 구글 광고 설정에서 개인화를 끌 수 있다는 점을 담는다.
- **`about/disclaimer.md`** — 면책조항. 각 챕터 하단 고지(투자 권유 아님, 제도·세금 변경 가능)의 사이트 단위 버전.
- **`about/contact.md`** — 문의처. `yshyuk.63@gmail.com`.

문의 이메일은 애드센스 계정 이메일과 다르다. 애드센스가 요구하는 것은 방문자가 운영자에게 연락할 수 있는 창구이고 계정 로그인 이메일은 방문자에게 노출되지 않으므로 문제없다. 다만 지급·본인확인 관련 구글 메일은 애드센스 계정 이메일로만 오고, 정책 위반 신고·저작권 문제 제기는 이 문의 주소로 들어온다.

## 11. SEO

챕터 frontmatter가 이미 SEO를 염두에 두고 작성되어 있다(`description`이 검색 미리보기용 문장으로 쓰여 있음). 그대로 활용한다.

| frontmatter | 쓰임 |
|---|---|
| `title` | `<title>` · og:title · JSON-LD `headline` |
| `description` | meta description · og:description |
| `date` | article:published_time |
| `keywords` | JSON-LD · 검색 가중치 (meta keywords는 무의미하므로 쓰지 않음) |
| `part` / `order` | 목차 정렬 · BreadcrumbList |

추가로 설정하는 항목:

- `lang: 'ko-KR'`, `og:locale=ko_KR`, `og:type=article`
- canonical (절대 URL)
- `sitemap: { hostname: 'https://stock-wiki.digestive-coffee.blog' }` — VitePress 내장 기능
- `public/robots.txt`
- JSON-LD 구조화 데이터: `Article` + `BreadcrumbList`(파트 → 챕터)

호스트명은 설정 상수 한 곳에 두어 도메인이 바뀌어도 한 줄만 고치면 되게 한다.

## 12. 배포

### 12.1 저장소 공개

현재 `stock-wiki`는 원격이 없는 로컬 저장소이며 `main` 단일 브랜치를 쓰고 있다. **GitHub 공개 저장소를 만들어 푸시한다.** `gh`가 `yshyuk` 계정으로 인증되어 있다.

공개 시 `docs/handoffs.md`와 `.superpowers/` 작업 로그도 GitHub에서 열람 가능해진다. 민감 정보는 없으나(집필 메모·출처 추적) 인지한 상태로 진행한다.

### 12.2 Cloudflare Pages

| 항목 | 값 |
|---|---|
| 프로덕션 브랜치 | `main` |
| 빌드 명령 | `npm run build` |
| 출력 디렉터리 | `.vitepress/dist` |
| Node 버전 | `.nvmrc`로 22 고정 |
| 커스텀 도메인 | `stock-wiki.digestive-coffee.blog` |

브랜치 모델은 이 저장소가 써 온 `main` 단일 브랜치를 유지한다(전역 규칙의 release + develop 모델과 다르지만 기존 이력을 따른다). 사이트 구축 작업은 `feat/site` 브랜치에서 진행하고 PR로 `main`에 머지한다.

### 12.3 도메인 연결 — 외부 DNS + CNAME

`digestive-coffee.blog`의 DNS는 **호스팅kr에서 관리 중이며 Cloudflare로 이전하지 않는다.**

Cloudflare Pages는 외부 DNS에 있는 도메인도 커스텀 도메인으로 받아주며, 단 **서브도메인만** 가능하다(apex 도메인은 네임서버를 Cloudflare로 옮겨야 한다). 우리 대상이 `stock-wiki.digestive-coffee.blog`이므로 이 방식이 그대로 적용된다.

**네임서버 이전을 기각한 이유**: 이전 시 Cloudflare가 기존 레코드를 자동 임포트하지만 완전하지 않다. `digestive-coffee.blog`에 운영 중인 서비스나 메일(MX) 레코드가 있으면 끊길 위험이 있고, 서브도메인 하나를 붙이기 위해 감당할 위험이 아니다.

**순서 의존성 — 반드시 지킬 것.** Cloudflare 문서가 명시적으로 경고하는 항목이다. Pages 대시보드에서 도메인을 먼저 등록하지 않고 CNAME만 만들면 도메인이 해석되지 않는다.

1. GitHub 공개 저장소 생성 → 푸시
2. Cloudflare Pages 프로젝트 생성 (GitHub 연동)
3. **Pages 대시보드 → 커스텀 도메인에 `stock-wiki.digestive-coffee.blog` 추가**
4. 호스팅kr DNS에 CNAME 추가 — 대상: `<프로젝트명>.pages.dev`
5. Cloudflare가 검증 후 SSL 인증서 자동 발급

4단계의 이름 칸에 호스트명(`stock-wiki`)만 넣는지 FQDN 전체를 넣는지는 호스팅kr UI 규약에 따른다. 해당 단계에서 확인한다.

근거: https://developers.cloudflare.com/pages/configuration/custom-domains/

### 12.4 그 밖의 전제조건

- Node는 nvm에 v22.23.1 / v24.15.0이 설치되어 있으나 비대화형 셸에서 `node`가 잡히지 않는다. `.nvmrc`와 함께 빌드 경로를 명시해야 한다.

전부 통과해야 완료로 본다. 각 항목은 실제 명령 실행 또는 산출물 확인으로 증명한다.

6. 사이드바에 39개 챕터가 모두 표시되고, 완성 13개만 활성 상태
7. 3단 레이아웃 · 다크모드 · 모바일 뷰 확인
8. 정책 페이지 3개가 푸터에서 전 페이지에 연결됨
9. `sitemap.xml`에 13개 챕터 + 랜딩 + 정책 페이지가 절대 URL로 포함됨

## 15. 확인이 필요한 사항

- **`digestive-coffee.blog`에 이미 다른 콘텐츠가 있는지.** 애드센스에 사이트를 추가할 때 상위 도메인 단위로 잡힐 가능성이 있어, 같은 도메인의 다른 콘텐츠가 심사 대상에 함께 들어갈 수 있다. 신청 전에 확인이 필요하다. (DNS 연결 자체는 12.3의 CNAME 방식으로 해결되어 더 이상 미해결 사항이 아니다.)
